# ТЗ для агента-разработчика: VAG Dashboard для Android

## 1. Цель проекта

Разработать самостоятельное Open Source Android-приложение для получения расширенной телеметрии автомобилей Volkswagen, Audi, Skoda, Seat и Cupra через ELM327 с отображением данных на настраиваемых приборных панелях.

Приоритетная платформа: MQB. Архитектура должна предусматривать расширение поддержки MQB Evo, MQB A0, MLB, MLB Evo, PQ35, PQ46 и MEB с учетом ограничений диагностического оборудования.

Основная задача заключается в получении максимально возможного количества параметров автомобиля, а не только стандартных OBD-II PID.

Приложение должно работать без Torque, Car Scanner, OBDeleven, облачных сервисов, обязательной регистрации и Google Mobile Services.

## 2. Базовый репозиторий

Используй в качестве основы:

https://github.com/gdm0991/vagdiag

Лицензия MIT.

Основная директория для разработки:

`android-app/`

Необходимо создать самостоятельный форк с отдельным applicationId, названием, иконкой и возможностью установки одновременно с оригинальным VAG Diag.

Перед разработкой:

- Изучи исходный код Android-версии.
- Изучи Python-версию, поскольку она может содержать диагностические алгоритмы, отсутствующие в Android.
- Изучи ARCHITECTURE.md, документацию, тесты, issues и историю изменений.
- Определи реализованные диагностические протоколы и ограничения.
- Сохрани рабочие механизмы подключения к автомобилю.
- Переиспользуй существующий код там, где это технически оправдано.
- Не переписывай рабочее диагностическое ядро без необходимости.

Основной продуктовый акцент нового приложения: непрерывная телеметрия и приборные панели, а не сервисная диагностика.

## 4. Целевое окружение

Основное устройство для тестирования:

- Android-смартфон без GMS. Конкретная модель в репозитории не фиксируется.
- Android Auto через AARE или его пользовательский форк.
- Подключение к автомобилю через ELM327.

Приоритетная платформа: MQB. Конкретная модель автомобиля, блоки и версии
прошивок в репозитории не фиксируются: фактические идентификаторы и
поддерживаемые параметры определяются диагностикой.

Архитектура не должна быть жестко привязана к конкретному автомобилю.

## 5. Диагностическое ядро

Реализовать или расширить поддержку:

### Транспорт

- Bluetooth Classic SPP.
- Bluetooth Low Energy.
- Wi-Fi TCP.
- USB OTG.
- Автоматическое переподключение.
- Определение возможностей адаптера.
- Контроль тайм-аутов.
- Обработка ошибок дешевых ELM327-клонов.
- Управление очередью запросов.
- Восстановление соединения без перезапуска приложения.

### Протоколы

- OBD-II.
- ISO 15765-4 CAN.
- ISO-TP.
- UDS ISO 14229.
- KWP2000 для совместимых автомобилей.
- TP2.0 при наличии поддержки соответствующим адаптером.
- 11-битная и 29-битная CAN-адресация.
- Многокадровые диагностические ответы.
- Physical и Functional Addressing.

Предусмотреть отдельные транспортные реализации для CAN FD и DoIP в будущем. Не заявлять их поддержку через обычный ELM327.

### Определение автомобиля

При первом подключении:

1. Прочитать VIN, если доступен.
2. Определить доступные электронные блоки.
3. Получить идентификаторы блоков и номера деталей.
4. Определить версии программного обеспечения.
5. Получить ASAM/ODX-идентификаторы, если доступны.
6. Подобрать подходящие диагностические профили.
7. Проверить доступность описанных в профиле параметров.
8. Сохранить результат в локальный профиль автомобиля.

Предусмотреть ручной выбор и корректировку профиля.

Не выполнять бесконтрольный перебор диагностических команд во время движения.

## 6. Каталог диагностических параметров

Создать универсальный расширяемый каталог сигналов, независимый от интерфейса и диагностического транспорта.

Поддержать:

- Стандартные OBD-II PID.
- Расширенные UDS DID.
- Импорт OBDb.
- Импорт легально доступных ODX/PDX.
- Импорт результатов обработки ASAM-MCD.
- Пользовательские PID и DID.
- Пользовательские формулы декодирования.
- Вычисляемые показатели на основе нескольких сигналов.
- Импорт и экспорт JSON-профилей.

Для каждого сигнала хранить:

- Уникальный идентификатор.
- Название на русском и английском языках.
- Категорию.
- Электронный блок.
- Диагностический протокол.
- Адрес запроса и ответа.
- PID или DID.
- Формат ответа.
- Смещение и длину значения.
- Порядок байтов.
- Знаковость.
- Формулу преобразования.
- Единицу измерения.
- Допустимый диапазон.
- Рекомендуемую частоту опроса.
- Условия доступности.
- Требуемую диагностическую сессию.
- Совместимые ECU и версии ПО.
- Источник определения.
- Статус проверки на реальном автомобиле.

Не выдумывать идентификаторы, формулы и значения.

Не считать сигнал подтвержденным только на основании его наличия в стороннем репозитории.

Разделять параметры по статусам: описан, обнаружен, успешно прочитан, декодирован, подтвержден на реальном автомобиле.

## 9. Движок телеметрии

Создать отдельный Telemetry Engine, отвечающий за:

- Управление подписками на параметры.
- Приоритизацию запросов.
- Адаптивную частоту опроса.
- Кэширование последних значений.
- Декодирование диагностических ответов.
- Вычисляемые показатели.
- Контроль актуальности данных.
- Запись истории.
- Восстановление соединения.
- Контроль нагрузки на диагностическую шину.

Целевые частоты при достаточной производительности оборудования:

| Параметры | Частота |
|---|---|
| Обороты, скорость, наддув | 5–10 Гц |
| Передача, момент, педаль газа | 2–5 Гц |
| Топливная система | 1–2 Гц |
| Температуры | 0,5–1 Гц |
| Электрика | 0,2–0,5 Гц |
| Диагностика | По запросу |

Частоты являются целевыми, а не гарантированными.

Не опрашивать весь каталог одновременно. Активный дашборд должен получать приоритет.

Использовать объединение запросов только там, где это поддерживается конкретным ECU.

Обеспечить единое соединение с адаптером для всех потребителей телеметрии.

## 12. Интеграция с AARE

Исследуй исходный код:

https://github.com/prototux/AARE

Основная цель: отображение собственных приборных панелей на головном устройстве автомобиля.

Предусмотреть:

- Независимую работу диагностического сервиса.
- Отдельный интерфейс автомобильного экрана.
- Поддержку нескольких пользовательских дашбордов.
- Управление переключением экранов.
- Адаптацию под доступное разрешение.
- Корректную работу в полноэкранном режиме и внутри составных рабочих столов AARE, если это поддерживается выбранной реализацией.
- Передачу телеметрии через локальный IPC или другой технически обоснованный интерфейс.
- Отсутствие необходимости повторного подключения к ELM327.

Не использовать закрытый API Torque.

Отдельно исследовать совместимость со штатным Android Auto. Не считать ее гарантированной из-за ограничений категорий приложений и способов проекции.

Все данные хранятся локально.

## 14. Безопасность

Приложение предназначено для мониторинга.

По умолчанию разрешены только диагностические операции чтения из утвержденного списка.

Запретить в новом интерфейсе:

- Кодирование блоков.
- Изменение адаптаций.
- Запись в ECU.
- Прошивку блоков.
- Управление исполнительными механизмами.
- Принудительную регенерацию DPF.
- Обход SFD и Security Access.
- Сброс блоков.
- Автоматическое удаление ошибок.

Не импортировать произвольные диагностические команды из пользовательских профилей без проверки.

Не выполнять тяжелое сканирование во время движения.

Не отправлять данные автомобиля сторонним сервисам.

Проверить зависимости на наличие аналитики, трекеров, внешних сетевых запросов и известных уязвимостей.

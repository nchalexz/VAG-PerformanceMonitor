# Отчёт 0.6.0: оптимизация частоты опроса телеметрии

Задание — [TELEMETRY_OPTIMIZATION.md](TELEMETRY_OPTIMIZATION.md).
Сборка — 0.6.0, `versionCode` 8. Дата — 27 ноября 2026.

Главное ограничение отчёта: **на реальном ELM327 и автомобиле 0.6.0
не проверялась**. Всё, что ниже помечено «проверено», проверено
JVM-тестами на поддельном источнике и поддельном транспорте. Целевые
частоты из задания не считаются достигнутыми без измерений на адаптере.

## 1. Что изменено в ядре

| Было (0.5.1) | Стало (0.6.0) |
|---|---|
| Выбор «самый давно прочитанный просроченный сигнал» | `TelemetryScheduler`: приоритетная очередь P0/P1/P2, дедлайн у каждого параметра |
| Порог устаревания `max(6 с, 6 × интервал)` | 5 с для P0/P1, 30 с для P2, как в задании |
| Ошибка чтения делала значение «—» сразу | ошибка сохраняет последнее число до истечения срока; «—» только по возрасту |
| «—» и для никогда не читанного | `NEVER_READ` → `N/A` |
| Один интервал из `pollHz`, без учёта задержки | интервал растёт от фактической задержки; при перегрузке замедляются P2, затем P1 |
| Пауза после отказа 1…15 с | таймаут: 1/2/4/8/15 с; NRC и «нет ответа» на DID: 15/30 с с перепроверкой |
| Каждый UDS DID — отдельный запрос | пакет `22 DID1 DID2 …` после одноразовой проверки на блоке |
| Диагностика и телеметрия мешали друг другу | `AdapterBus`: одна логическая операция на шине |
| Метрик не было | `TelemetryMetrics` + экспорт JSON из настроек |

Файлы:

- `telemetry/TelemetryScheduler.kt` — расписание, приоритеты, backoff,
  адаптивные интервалы, пакеты DID.
- `telemetry/TelemetryMetrics.kt` — метрики и кольцевой журнал.
- `telemetry/TelemetryDiagnostics.kt` — экспорт JSON без VIN.
- `telemetry/TelemetryEngine.kt` — цикл опроса поверх планировщика,
  состояния актуальности, пересчёт производных.
- `telemetry/SignalSource.kt` — классификация отказов, пакетное чтение,
  откат к одиночным запросам.
- `telemetry/Signal.kt` — приоритеты, `SignalStatus`, `GearLabel`.
- `telemetry/SignalCatalog.kt` — таблица приоритетов и пометка передачи.
- `core/AdapterBus.kt`, `core/Uds.kt` — общая блокировка шины, NRC в ошибке.
- `telemetry/TelemetryRepository.kt` — монотонные часы, метрики последней
  сессии, запасные источники, экспорт.
- `DiagViewModel.kt` — диагностика берёт шину целиком.
- Настройки, виджет, мост DashGrid — состояния `VALID`/`STALE`/`NEVER_READ`,
  P/R/N у передачи.

## 2. Приоритеты и сроки

| Приоритет | Сигналы | Целевая частота | Актуальность |
|---|---|---|---|
| P0 | обороты, скорость, наддув, MAP/BARO, масло, ОЖ | 10 Гц для оборотов и скорости, 1–10 Гц для остальных | 5 с |
| P1 | момент, мощность, передача, педаль, давление топлива | 2–5 Гц | 5 с |
| P2 | DSG, DPF, коррекции, остальная диагностика | 0,2–1 Гц | 30 с |

Приоритет влияет на очередь, а не на гарантию частоты. Параметр, который
ждал 3 и 6 секунд, поднимается в очереди на одну-две ступени, поэтому P2
не откладывается бесконечно.

## 3. Результаты тестов

```
./gradlew :app:testStandardDebugUnitTest
98 tests, 0 failures
./gradlew :app:assembleStandardDebug :app:assembleAaDebug
BUILD SUCCESSFUL
```

Все 12 сценариев из раздела 8 задания покрыты `TelemetryEngineScenarioTest`:

1. успешное получение параметра;
2. параметр никогда не был прочитан → `N/A`;
3. единичный таймаут без исчезновения значения;
4. устаревание частого параметра через 5 с;
5. устаревание редкого параметра через 30 с;
6. восстановление после серии ошибок;
7. нулевое значение — значение, а не прочерк;
8. полная потеря связи → `STALE`;
9. медленный адаптер: одна транзакция, интервал ≥ задержка × 1,15;
10. неподдерживаемый DID: 1–3 попытки за минуту, не каждый цикл;
11. перегрузка очереди: глубина ограничена, редкие параметры не голодают;
12. несколько подписчиков делят одну очередь.

Дополнительно: `TelemetrySchedulerTest` (11 проверок), `TelemetryMetricsTest`
(5), пакетный DID и откат в `Elm327UdsSourceTest` (2), P/R/N
в `MetricRegistryTest` (2).

## 4. Как измерить на реальном ELM327

1. Подключить адаптер, открыть приборку (она задаёт набор P0/P1) и дать
   2–3 минуты непрерывного опроса.
2. **Настройки → Диагностика телеметрии** → **Экспорт журнала**.
3. Передать JSON на компьютер (файл в `cacheDir/diagnostics`).
4. Смотреть:
   - `metrics.requestRateHz` — фактическая нагрузка на шину;
   - `metrics.averageLatencyMs`, `metrics.p95LatencyMs`;
   - `metrics.successPercent`, `metrics.timeouts`, `metrics.ecuSwitches`;
   - `metrics.signals[].updatesPerSecond` — фактическая частота параметра;
   - `metrics.signals[].ageMs` и `staleTransitions`;
   - `metrics.queueDepth`;
   - `schedule[].effectiveIntervalMs`, `suspendedUntilMs`,
     `consecutiveFailures`.
5. Целевые 10 Гц считаются достигнутыми, только если
   `updatesPerSecond` для оборотов и скорости на этом адаптере близко
   к 10, а `successPercent` не падает. Иначе честный вывод — «адаптер
   не тянет», и в отчёте должна остаться измеренная цифра.

Полезно прогнать два сценария: одна подписка (приборка) и приборка +
каталог Live Data, и сравнить `requestRateHz` и `updatesPerSecond`.

## 5. Соответствие критериям приёмки (раздел 9)

| Критерий | Состояние |
|---|---|
| Приоритетные показатели обновляются с максимально доступной частотой | **не проверено на железе**; логика и тесты есть |
| Редкие параметры не препятствуют приоритетным | проверено тестами планировщика |
| Единичные ошибки не вызывают прочерков | проверено тестом |
| Устаревшие значения не выдаются за актуальные | проверено тестами 5/30 с |
| Ни разу не полученные — `N/A` | проверено тестом |
| Нет конкурирующих подключений | `Telemetry` — один владелец, `AdapterBus` сериализует диагностику |
| Поддержка профилей сохранена | профили не менялись |
| Дизайн экранов и виджетов сохранён | менялись только подписи состояний и передача |
| Команды изменения кодировок/адаптаций не отправляются | по-прежнему только `22` и `3E` |

## 6. Что осталось непроверенным

- Фактические частоты и задержки на живом ELM327, особенно на клонах v1.5.
- Пакетный `22 DID1 DID2` на конкретном блоке MQB: проверка есть в коде,
  но не на машине.
- P/R/N и вообще семантика DID 210F на живом DSG.
- Поведение при поездке: питание, переподключение, нагрев адаптера.
- Виджет и Android Auto на реальном хосте.

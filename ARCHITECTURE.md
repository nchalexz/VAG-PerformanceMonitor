# Архитектура

Версия 0.2.0 (первая тестовая реализация). Документ описывает то, что уже
есть в коде, и честно отмечает то, чего ещё нет. Полное техническое задание —
[`docs/SPEC.md`](SPEC.md).

## Слои

```
Compose (cockpit/, ui/)
        │  StateFlow<CockpitUiState>
CockpitViewModel
        │
TelemetryEngine  ──►  SignalCatalog (чистые данные)
        │
SignalSource (интерфейс)
        ├── DemoSignalSource   — модель, без автомобиля
        └── Elm327SignalSource — OBD-II mode 01
                    │
                 Elm327  ──►  Transport (Wi-Fi / Bluetooth / USB)
```

Стрелки идут только вниз. Каталог не знает о движке, движок — об Android,
интерфейс — о транспорте. Это позволяет проверять декодирование и
расписание опроса обычными JVM-тестами.

## Пакеты

| Пакет | Ответственность |
|---|---|
| `core/` | Транспорты (Wi-Fi, Bluetooth SPP, USB serial), ELM327, ISO-TP, UDS, коды ошибок. Унаследовано от VAG Diag и сохранено без переписывания. |
| `core/AdapterHolder.kt` | Одно соединение с адаптером на процесс. Диагностика открывает — приборка переиспользует. |
| `telemetry/Signal.kt` | `SignalDefinition`, `ValueSpec`, `ComputedSpec`, статусы, `SignalValue`. |
| `telemetry/SignalCatalog.kt` | Встроенный каталог: 41 стандартный OBD-II PID, 3 вычисляемых, 1 виртуальный. |
| `telemetry/ObdPayload.kt` | Разбор ответов с CAN-ID и без, ISO-TP и «сырых» строк. |
| `telemetry/SignalSource.kt` | Интерфейс источника, демонстрационная модель, чтение OBD-II через ELM327. |
| `telemetry/TelemetryEngine.kt` | Подписки, приоритеты, адаптивная частота, backoff, кэш, вычисляемые показатели. |
| `telemetry/Dashboard.kt` | Описание экранов и виджетов, диапазоны и пороги. |
| `cockpit/` | Экран приборов: «Движение», «Динамика», «Данные», переключение ДЕМО/ELM327. |
| `ui/` | Диагностическая часть VAG Diag (подключение, блоки, ошибки, отчёты). |

## Движок телеметрии

Один корутинный цикл на всё приложение-экран. Запросы никогда не идут
параллельно: у ELM327 один последовательный канал, а дешёвые клоны не
переносят два запроса подряд — это выяснено ещё в базовом проекте.

Два класса подписок:

- **активный дашборд** — каждый сигнал опрашивается со своей частотой
  (`pollHz`), просроченные запросы идут первыми;
- **каталог Live Data** — по одному сигналу в свободное время, по кругу.
  Пока приборка получает данные, список параметров не отбирает шину.

При отсутствии ответа включается экспоненциальный backoff (1 с … 15 с),
поэтому неподдерживаемый PID не долбится десять раз в секунду. Значение
считается устаревшим, если ему больше `max(3 с, 4 × интервал)`; интерфейс
показывает «—», а не последнее число и не ноль.

Вычисляемые показатели:

| Показатель | Формула | Зависимости |
|---|---|---|
| Момент, Н·м | PID 0x62 / 100 × PID 0x63 | фактический момент, опорный момент |
| Мощность, кВт | момент × обороты / 9549 | момент, PID 0x0C |
| Наддув, кПа | PID 0x0B − PID 0x33 | давление во впуске, атмосферное |

Если входных данных нет или они устарели, вычисляемый показатель тоже
становится «нет данных».

## Общее соединение

`MainActivity` и `CockpitActivity` живут в одном процессе. Диагностический
экран после `init()` адаптера кладёт объект в `AdapterHolder`, приборка
берёт его оттуда. Второе соединение не открывается.

`Elm327.command` помечен `@Synchronized`: даже если пользователь запустит
сканирование и одновременно откроет приборку, команды не переплетутся
внутри одного объекта. Это защита от гонки команд, но не от логической
конкуренции за шину: сканирование блоков и телеметрия одновременно
замедлят друг друга. В текущей версии это осознанно оставлено на
ответственность пользователя и вынесено в ограничения.

## Что не реализовано

- Профили автомобилей и динамическое определение ECU (только каталог
  сигналов и ручной выбор источника).
- UDS DID в движке телеметрии: идентификация блоков есть в `core/Uds.kt`,
  но в каталог и на приборку расширенные DID не заведены.
- Запись поездок, история, экспорт.
- Конструктор дашбордов (экраны пока описаны в коде).
- Android Auto / AARE.
- Многомодульная структура из ТЗ: сейчас один модуль `app`, пакеты
  повторяют будущие модули. Дробить на Gradle-модули до появления
  второго потребителя телеметрии — лишняя работа.

## Расширение

Чтобы добавить сигнал, достаточно записи в `SignalCatalog`:

```kotlin
obd(
    id = "engine.oil_pressure",
    nameRu = "Давление масла",
    nameEn = "Engine oil pressure",
    category = SignalCategory.ENGINE,
    pid = 0x??,
    spec = ValueSpec(length = 1, scale = 1.0),
    unit = "кПа", decimals = 0,
    min = 0.0, max = 1000.0, pollHz = 1.0,
)
```

Если PID/DID и формула не подтверждены документально или на машине —
сигнал не добавляется. Статус `CONFIRMED` ставится только после чтения
на реальном автомобиле.

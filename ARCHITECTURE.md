# Архитектура

Версия 0.6.0 (тестовая реализация). Документ описывает то, что уже есть
в коде, и честно отмечает то, чего ещё нет. Полное техническое задание —
[`docs/SPEC.md`](docs/SPEC.md).

## Слои

```text
CockpitActivity   AppWidget   CarAppService (aa)   SettingsActivity
        └──────────────┴───────────────┴──────────────────┘
                 Telemetry (singleton, StateFlow)
                              │
                       TelemetryEngine  ──►  SignalCatalog
                              │
                       SignalSource
                       ├── DemoSignalSource   — модель, без автомобиля
                       └── Elm327SignalSource — OBD-II mode 01
                              │
                           Elm327  ──►  Transport (Wi-Fi / Bluetooth / USB)

TelemetryService — foreground, уведомление, обновление виджетов
```

Стрелки идут только вниз. Каталог не знает о движке, движок — об Android,
интерфейс — о транспорте. Это позволяет проверять декодирование и
расписание опроса обычными JVM-тестами.

Отдельно стоит диагностический экран VAG Diag: он работает с собственным
`Elm327` и не входит в дерево телеметрии.

## Общее состояние

`Telemetry` инициализируется в `AapmApp` и живёт в процессе приложения.
При старте он:

1. загружает профиль автомобиля и кэш последних значений;
2. поднимает демонстрационный источник;
3. если сохранён адаптер и разрешено автоподключение — открывает соединение
   и заменяет источник на ELM327.

Представления не создают движок. Они вызывают `subscribe(key, ids)` и
читают `Telemetry.state`. Ключи подписок не пересекаются: `cockpit`,
`widgets`, `profile`. Движок получает объединение наборов, поэтому
приборка и виджет не отбирают шину друг у друга.

`TelemetryService` не открывает соединение. Его задачи — foreground-статус,
уведомление с кнопкой отключения и обновление виджетов. Пока служба жива,
процесс и подписки сохраняются при свёрнутой Activity.

Автоматического переподключения после обрыва пока нет: автоподключение
работает только при запуске приложения.

## Движок телеметрии

Один корутинный цикл на источник. Запросы никогда не идут параллельно:
у ELM327 один последовательный канал, а дешёвые клоны не переносят два
запроса подряд — это выяснено ещё в базовом проекте. С 0.6.0 расписание
считает `TelemetryScheduler`, а движок только выполняет его решения.

### Планировщик

У каждого параметра в очереди есть приоритет, интервал, время последней
попытки, число отказов подряд, сглаженная задержка ответа и пауза после
сбоя. Выбор следующего запроса:

1. берутся только созревшие параметры: `lastAttempt + interval ≤ now`,
   и пауза после отказа истекла;
2. выше идёт P0, затем P1, затем P2;
3. параметр, который ждёт дольше 3 и 6 секунд, поднимается на одну-две
   ступени — так P2 не откладывается бесконечно при насыщенной шине;
4. при равенстве выбирается тот, кто ждёт дольше; для UDS к нему
   добавляются созревшие DID того же блока (до четырёх) — пакетный запрос
   включается только после успешной проверки на этом блоке.

Интервал параметра — максимум из целевого (`pollHz`), фактической задержки
ответа × 1,15 и минимума ступени (100 мс у экрана, 1 с у фона и каталога).
При перегрузке адаптера (сглаженная задержка выше 150 мс) P1 и P2
замедляются до трёх раз, P0 сохраняет темп.

Результат опроса обрабатывается по-разному:

| Результат | Что делает планировщик |
|---|---|
| OK | сбрасывает отказы и паузу, обновляет задержку |
| Таймаут / сбой транспорта | пауза 1, 2, 4, 8, затем 15 с |
| Отрицательный ответ UDS (`NRC`) | пауза 15 с для P0/P1 и 30 с для P2 |
| Нет ответа на DID | то же: параметр перепроверяется, но не долбится |

### Актуальность

`SignalValue` хранит последнее число, время успеха, время попытки, признак
«хоть раз прочитан» и число отказов. `statusAt` даёт `VALID`, `STALE` или
`NEVER_READ`:

- ошибка чтения не стирает число — оно живёт до истечения срока;
- P0/P1 свежи 5 секунд, P2 — 30 секунд;
- если успешного чтения не было ни разу, это `NEVER_READ` (`N/A`), а не «—»;
- возраст считается по монотонным часам (`SystemClock.elapsedRealtime`),
  проверка идёт и без новых ответов, поэтому потеря связи сама переводит
  значения в `STALE`.

### Метрики

`TelemetryMetrics` считает по каждому параметру число попыток и успехов,
таймауты, отрицательные ответы, сбои транспорта, среднюю и P95 задержку,
фактическую частоту обновлений, возраст и переходы в `STALE`, а глобально —
запросы/с, процент успеха, переключения ECU и глубину очереди. Последние
события хранятся в кольцевом журнале; `TelemetryDiagnostics` пишет его
в JSON по нажатию в настройках.

Вычисляемые показатели:

| Показатель | Формула | Зависимости |
|---|---|---|
| Момент, Н·м | PID 0x62 / 100 × PID 0x63 | фактический момент, опорный момент |
| Мощность, кВт | момент × обороты / 9549 | момент, PID 0x0C |
| Наддув, кПа | PID 0x0B − PID 0x33 | давление во впуске, атмосферное |

Если входных данных нет или они устарели, вычисляемый показатель тоже
становится «нет данных».

## VAG UDS

Кроме OBD-II каталог содержит 83 сигнала, которые читаются командой
`22 <DID>` у конкретного блока: двигатель `7E0`/`7E8`, коробка `7E1`/`7E9`,
щиток `714`/`77E`, датчик АКБ `710`/`77A`. Описание сигнала хранит адреса,
DID, битовое смещение и длину, знак, порядок байтов и формулу
`(raw × mul ÷ div) + add` (`UdsValueSpec`).

`Elm327SignalSource` маршрутизирует чтение по `SignalDefinition.isUds`:

- OBD идёт на функциональный адрес `7DF`, UDS — на адрес блока;
- перед каждым UDS-запросом выставляется `ATSH <tx>`, при обрезанном
  многокадровом ответе `UdsClient` перебирает `ATCRA`/flow-control;
- ответ на DID кэшируется на 250 мс: несколько сигналов одного блока часто
  лежат в одном ответе;
- следующий OBD-запрос заново выставляет `7DF`, иначе он уйдёт не в двигатель.

Безопасность: отправляются только `22` (чтение) и `3E` (keep-alive). Сигналы
с требованием `10 03` в набор не попали. Кодирования, адаптаций, тестов
исполнительных механизмов и стирания ошибок в телеметрии нет.

Источник данных — открытый набор OBDb/Audi-Q3 (CC BY-SA 4.0, commit
`b51e835`), сгенерированный `tools/obdb_import.py`. Все сигналы имеют статус
`DECODED`; ни один не подтверждён на автомобиле. Список и происхождение —
`SIGNAL_CATALOG.md`, дизайн интерфейса — `docs/UI.md`.

## Поверхности

| Представление | Как получает данные | Ограничение |
|---|---|---|
| Приборка | `Telemetry.subscribe("cockpit", …)`, `StateFlow` | Compose, полный экран |
| Виджет | `WidgetPublisher` из `TelemetryService`, не чаще ~3 раз в секунду | `RemoteViews`, 4 параметра или 2 |
| Android Auto | `CarAppService`, `ListTemplate`, до 8 параметров профиля (OBD-II) | только шаблоны хоста, без Canvas |
| Настройки | читает и меняет `Telemetry`, профиль и адаптер | Compose |

VAG-сигналы в шаблонный список Android Auto не попадают: он берёт набор
профиля (OBD-II). Полный VAG-набор виден в приборке и каталоге.

Виджет хранит конфигурацию по `appWidgetId`, поэтому несколько экземпляров
могут показывать разные наборы. Обновление идёт из службы, а не через
`updatePeriodMillis`: период в минутах для телеметрии бесполезен.

## Мост для DashGrid

`bridge/TelemetryProvider` — экспортированный read-only `ContentProvider`
с authority `io.github.nchalexz.aaperfmon.telemetry`. DashGrid вызывает
`call("snapshot")` и получает Bundle контракта v1: состояние связи, статус,
`updatedAt` и JSON-массив сигналов, сгруппированный по шести экранным
категориям. Сигнал отдаётся в единицах приборки (наддув — бар), с `raw`
для стрелки и флагами `stale`/`warning`.

`bridge/TelemetrySnapshot` собирает снимок из `Telemetry.state.value` и
`MetricRegistry`: это слой отображения, а не второй движок. В ДЕМО он берёт
значения из той же `DemoSignalSource` по запросу, поэтому чтение не
запускает службу, не подключает адаптер и не опрашивает PID. Разрешение
`READ_TELEMETRY` — `normal`, только чтение; подробности — в
[`docs/AARE_DASHGRID.md`](docs/AARE_DASHGRID.md) и [`SECURITY.md`](SECURITY.md).

Инициализация `Telemetry.init` больше не подключает сохранённый адаптер:
автоподключение вынесено в `autoConnectOnce()` и вызывается экраном,
приборкой или службой. Процесс, поднятый чтением провайдера, остаётся
в ДЕМО и не открывает OBD.

## Соединение с адаптером

Телеметрия владеет одним соединением. Приборка, виджет и автомобильный
экран переиспользуют его через `Telemetry`, второй сессии OBD нет.

Диагностический экран использует тот же `Elm327`, когда телеметрия уже
подключена: `AdapterHolder` отдаёт общий объект. `AdapterBus` — корутинный
мьютекс, который берётся на всю логическую операцию: один опрос телеметрии,
скан блоков, чтение ошибок, живой опрос диагностики. Команды адаптера
дополнительно сериализуются `synchronized(elm)`, но мьютекс гарантирует,
что между `ATSH` и запросом сканирования не вклинится телеметрия
с заголовком `7DF`.

Пока диагностика держит шину, движок телеметрии ждёт; значения при этом
не обновляются и по сроку давности становятся `STALE`. Это сознательный
компромисс: корректный скан важнее непрерывности приборки.

## Профили и настройки

Профиль — это название, платформа, двигатель, коробка, необязательный VIN
и набор `signalIds`. Встроены два профиля: VAG MQB и универсальный
OBD-II. Пользователь может изменить набор параметров и сохранить профиль.
Автоматического определения по VIN нет: поле VIN существует, но не
используется для подбора.

`AdapterStore` хранит последнюю конфигурацию адаптера и флаг автоподключения.
`VehicleStore` хранит профиль. Оба — JSON в `SharedPreferences`; для
нескольких полей это дешевле Room.

## Android Auto

Сборка `aa` добавляет `CarAppService` и зависимость Car App Library 1.7.0.
Автомобильный экран — `ListTemplate`: состояние подключения и до восьми
параметров профиля. Штатный хост не разрешает произвольный Canvas, поэтому
полноэкранная приборка остаётся в `CockpitActivity`.

`HostValidator.ALLOW_ALL_HOSTS_VALIDATOR` нужен для сайдлоада и AARE.
Для публикации в Google Play потребуется белый список хостов и проверка
категории. Обычная сборка `standard` не содержит `CarAppService`.

## Что не реализовано

- Подтверждение VAG DID на живом MQB TDI; сейчас только статус «декодирован».
- DIDs, требующие расширенной сессии `10 03`; Haldex и часть DPF-параметров.
- Импорт ODX/PDX или VCDS-лейблов: только открытый набор OBDb.
- Определение автомобиля по VIN и автоматический подбор профиля.
- Запись поездок, история, экспорт, графики.
- Конструктор дашбордов (экраны пока описаны в коде).
- Автоматическое переподключение после обрыва.
- Интеграция с DashGrid: read-only провайдер есть с 0.5.0 и проверен
  с DashGrid 1.3.0 на эмуляторе; прогона на живом головном устройстве
  ещё нет. Приборку в AARE можно запустить как обычное Android-приложение,
  если хост это позволяет.
- KWP2000, TP2.0, BLE, CAN FD и DoIP.
- Многомодульная структура из ТЗ: сейчас один модуль `app`, пакеты
  повторяют будущие модули. Дробить на Gradle-модули до появления
  второго потребителя телеметрии — лишняя работа.

## Расширение

Чтобы добавить сигнал, достаточно записи в `SignalCatalog`:

```kotlin
obd(
    id = "engine.oil_pressure",
    nameRu = "Давление масла",
    nameEn = "Engine oil pressure",
    category = SignalCategory.ENGINE,
    pid = 0x??,
    spec = ValueSpec(length = 1, scale = 1.0),
    unit = "кПа", decimals = 0,
    min = 0.0, max = 1000.0, pollHz = 1.0,
)
```

Если PID/DID и формула не подтверждены документально или на машине —
сигнал не добавляется. Статус `CONFIRMED` ставится только после чтения
на реальном автомобиле.

## Дополнение 0.3.0: одно соединение на все представления

Изначально приборка владела собственным движком. В 0.3.0 появился
`telemetry/TelemetryRepository.kt` (`object Telemetry`) — единственный
владелец ELM327 и `TelemetryEngine`:

```
CockpitActivity ─┐
AppWidget       ─┼─► Telemetry.state (StateFlow) ◄─ TelemetryEngine ◄─ Elm327
CarAppService   ─┘              ▲
                         TelemetryService (foreground, виджет, уведомление)
```

- `Telemetry.init(context)` вызывается из `AapmApp`; по умолчанию поднимает
  демонстрационный источник.
- Настройки вызывают `Telemetry.connect(AdapterConfig)`. Соединение
  открывается один раз; все экраны подписываются на один `StateFlow`.
- `Telemetry.subscribe(key, ids)` объединяет подписки профиля, приборки и
  виджетов; движок получает объединение и сам добавляет зависимости
  вычисляемых сигналов.
- `ValueCache` сохраняет последние значения на диск, чтобы виджет после
  перезапуска показывал «устарело», а не пустоту.
- `TelemetryService` — foreground-сервис типа `connectedDevice`: держит
  процесс, показывает уведомление и обновляет RemoteViews. Он не открывает
  второе соединение.
- `WidgetPublisher` ограничивает частоту обновления RemoteViews (~3 Гц),
  частота опроса OBD остаётся прежней.

## Android Auto

AA-сборка добавляет `car/CarTelemetryService` (`CarAppService`) и
`ListTemplate` с показателями. Это единственный допустимый способ вывода
в штатном Android Auto: произвольный Canvas там запрещён. Полноэкранная
приборка предназначена для AARE/DashGrid, где приложение запускается как
обычное Android-приложение. Подробности — `docs/AA.md`.
